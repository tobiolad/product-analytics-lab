# Data dictionary

All data in this project is synthetic, generated by `generator/generate.py`
with a fixed seed (`SEED = 42` in `generator/constants.py`). Nothing here is
real user data. Tables below are as created by `db/sql/001_schema.sql`; views
are as created by `db/sql/002_views.sql`.

## Tables

### `accounts`

One row per signed-up company/workspace.

| Column | Type | Notes |
|---|---|---|
| `account_id` | VARCHAR, PK | |
| `signup_date` | DATE | Within `2026-01-01`–`2026-06-30` |
| `acquisition_channel` | VARCHAR, nullable | One of `organic_search`, `paid_search`, `referral`, `content_marketing`, `social`, `partner`. **~3% of accounts have this missing** (`NULL`) — a deliberately injected data quality issue simulating a dropped UTM parameter, not a bug in the queries that read it. |
| `plan_id` | VARCHAR | One of `free`, `starter`, `pro`, `enterprise`. 82% of signups start on `free` (freemium funnel). No later upgrades are modeled — this is the plan at signup time only. |

### `users`

One row per person. Every account has exactly one `owner` plus zero or more
`member` users.

| Column | Type | Notes |
|---|---|---|
| `user_id` | VARCHAR, PK | |
| `account_id` | VARCHAR, FK → `accounts` | |
| `role` | VARCHAR | `owner` \| `member` |
| `joined_date` | DATE | |

### `experiment_assignments`

Deterministic A/B assignment, one row per (user, experiment). Only the
account **owner** is assigned (onboarding is an owner-driven flow), and only
for accounts created within an experiment's eligibility window — see
`docs/EXPERIMENT_METHODOLOGY.md`.

| Column | Type | Notes |
|---|---|---|
| `user_id` | VARCHAR, FK → `users` | |
| `experiment_name` | VARCHAR | e.g. `onboarding_redesign_v1` |
| `variant` | VARCHAR | `control` \| `treatment` |
| `assigned_at` | DATE | |

### `sessions`

One row per login/usage session.

| Column | Type | Notes |
|---|---|---|
| `session_id` | VARCHAR, PK | |
| `user_id` | VARCHAR, FK → `users` | |
| `account_id` | VARCHAR, FK → `accounts` | |
| `started_at` | TIMESTAMP | |
| `ended_at` | TIMESTAMP, nullable | |

### `events_raw`

Raw, **undeduplicated** event stream — see "Known data quality issues" below.
Nothing in the API or `db/metrics.py` reads this table directly; everything
reads the `events` view instead.

| Column | Type | Notes |
|---|---|---|
| `event_id` | VARCHAR | **Not unique** — duplicates are intentional, see below |
| `user_id` | VARCHAR, FK → `users` | |
| `account_id` | VARCHAR, FK → `accounts` | |
| `session_id` | VARCHAR, nullable | `NULL` for onboarding-funnel events, which aren't tied to a browsing session |
| `event_name` | VARCHAR | See `docs/EVENT_TAXONOMY.md` |
| `event_timestamp` | TIMESTAMP | When the event actually happened (client clock) — the authoritative time for all cohorting/funnel logic |
| `received_at` | TIMESTAMP | When the event reached the server — can lag `event_timestamp` on late-arriving events |

## Views (the canonical read surface)

### `events`

`SELECT DISTINCT ON (event_id) ... FROM events_raw`. Deduplicates by
`event_id`. **Every metric query and the API read from this view, never from
`events_raw`.**

### `onboarding_progress`

One row per (user, onboarding step actually reached), joined to the account's
`signup_date`, with `days_since_signup` computed. The base table every
funnel/activation query builds on.

### `account_activation`

One row per account. `days_to_activation` is `NULL` if the account never
reached `completed_key_action`; `activated_within_7d` is `days_to_activation
<= 7`. **The single source of truth for "is this account activated"
everywhere else in the codebase.**

## Known data quality issues (intentional)

These are injected by `generator/generate.py` to mirror real event-pipeline
behavior, not left in by accident:

| Issue | Rate | Where it shows up |
|---|---|---|
| Duplicate event fires (same `event_id` twice) | ~1% of events | `events_raw` only — the `events` view's `DISTINCT ON` removes them |
| Late-arriving events (`received_at` 6–72h after `event_timestamp`) | ~2% of events | Both tables; funnel/cohort logic deliberately uses `event_timestamp`, not `received_at` |
| Missing `acquisition_channel` | ~3% of accounts | `accounts.acquisition_channel IS NULL` — shown as "Unknown" in the dashboard, never silently dropped from denominators |

If you query `events_raw` directly and get different funnel counts than the
dashboard, this is why — use the `events` view.
